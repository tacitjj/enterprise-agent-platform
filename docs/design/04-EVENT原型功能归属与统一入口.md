# EVENT 原型功能归属与点联统一入口

## 1. 结论

EVENT 原型的主体是“企业员工数字办公平台”，不是点联内部平台运营后台。它把企业员工日常工作、部分企业管理员动作和演示身份切换放在一个页面中，因此正式产品需要保留其统一工作体验，同时重新划清权限和事实归属。

点联采用以下三层结构：

| 层级 | 使用者 | 登录与入口 | 核心范围 |
|---|---|---|---|
| 企业工作平台 | 企业普通员工、审批人、任务/群参与者、企业管理员 | 企业成员统一登录后默认进入 | 组织大厅、消息、数字员工、任务、成果、个人待办和本人可见智点 |
| 企业管理域 | 同一企业账号中具备管理权限的成员 | 同一应用、同一登录态内按权限出现管理入口 | 招聘和配置企业数字员工、成员/部门、知识、群治理、审批、预算费用和企业监控 |
| 点联内部运营后台 | 点联运营、模板、定价、财务、SRE、审计 | 平台运营上下文；不使用企业活动租户 | 官方模板、能力包、模型/Provider、价格倍率、租户智点、成本对账和平台运行 |

“企业管理域”不是另一套账号，也不要求复制一套企业门户。普通员工看不到管理入口；管理员仍然先是当前企业成员，再按服务端权限进入对应管理页面。平台运营角色与企业角色不隐式继承。

## 2. EVENT 五个主入口的正式归属

| EVENT 入口/能力 | 正式归属 | 默认可见范围 | 点联需要的优化 |
|---|---|---|---|
| 组织大厅 | 企业工作平台 | 当前成员可见的组织、房间、真人、数字员工、任务摘要 | 固定九房间改为组织/项目/协作空间动态数据；无权房间只显示允许公开的能力和申请入口 |
| 消息 | 企业工作平台 | 本人单聊、已加入群聊及其历史策略允许的消息 | 普通消息零模型调用；只有选择、`@` 或回复数字员工才触发；接入 `USER_AGENT` / `GROUP_AGENT` 记忆边界 |
| 数字员工 | 企业工作平台的员工名册 | 当前成员被授权查看/使用的企业数字员工实例 | 所有人可看档案和开始工作；具备管理权限者额外看到招聘、配置、启用/停用入口 |
| 当前任务 | 企业工作平台 | 本人创建、负责、协作、审批或获授权查看的任务 | 管理员可按管理权限扩展到部门/企业监控，但正文仍按对象权限；展示真实 Step/Run/费用/成果而非演示百分比 |
| 智点明细 | 企业工作平台 | 本人或企业策略允许的部门/任务用量 | 企业费用管理员可进入企业聚合和账本；平台供应商底价、倍率和贡献额只进入点联内部运营后台 |

## 3. EVENT 中混杂功能的重新归位

| 原型行为 | 正式处理 |
|---|---|
| “切换演示身份” | 删除。身份、活动企业、角色、权限版本均来自服务端会话；多端共用同一账号和 JWT 契约 |
| 总经理“新增员工类型” | 移出企业工作平台。官方岗位类型由点联内部运营后台创建版本；企业只能从已发布模板招聘并定制实例 |
| 编辑数字员工名称和头像 | 保留为企业员工实例配置，由企业员工管理权限控制，不反向修改平台模板 |
| 在房间新增真人或数字员工 | 真人归企业成员/组织管理；数字员工只能选择企业已招聘实例或从官方模板招聘，不能在前端凭空创建 |
| 查看全公司任务和智点 | 保留为企业管理权限增强；部门管理员只看部门，普通员工只看本人/参与范围 |
| 固定组织、固定员工、固定任务和固定余额 | 全部改为真实 API/读模型，不作为失败回退 |
| 恢复演示初始数据、本地身份和 localStorage 事实 | 生产入口删除，仅可作为独立 Story/测试 Fixture，且不进入 API 构建 |

## 4. 数字员工与记忆隔离

每个企业数字员工都是独立的 `EnterpriseAgent`，冻结平台模板版本并拥有自己的企业配置、知识范围、模型策略、记忆策略和审批策略。数字员工的记忆不能只按用户或只按群存一份，而应同时绑定作用域和员工实例。

| 记忆作用域 | 唯一边界 | 允许用途 | 禁止行为 |
|---|---|---|---|
| `AGENT` | 企业 + 数字员工实例 | 该员工经治理确认的岗位经验 | 员工 A 默认读取员工 B 的岗位记忆 |
| `USER_AGENT` | 企业 + 真人用户 + 数字员工实例 | 该用户与该员工之间的私人习惯、表达偏好 | 进入群回答、被企业管理员默认读取、跨用户或跨员工召回 |
| `GROUP_AGENT` | 企业 + 群聊 + 数字员工实例 | 当前群与该员工共同确认的协作习惯 | 跨群召回；同群不同员工默认共享；成员离群后继续访问 |
| `PROJECT` | 企业 + 项目 | 项目事实和经确认经验 | 因同属企业就自动可见；绕过项目成员和知识 ACL |
| `CONVERSATION` | 当前会话 | 短期上下文和工作状态 | 自动升级为长期记忆 |

同一数字员工服务不同真人员工时，分别使用不同 `USER_AGENT`；同一群里的不同数字员工也分别拥有独立 `GROUP_AGENT`；长期偏好先形成 `MemoryCandidate`，经确认后才进入相应作用域。

## 5. 页面和路由原则

1. 企业成员登录后始终进入 EVENT 风格的统一企业工作平台。
2. 企业管理菜单由服务端权限决定。拥有 `enterprise.employee.read/execute` 只能查看或使用员工，不能因此进入员工管理；至少具备招聘、配置或启用等管理权限才显示员工管理入口。
3. 企业管理页继续复用 EVENT 的顶栏、左侧工作入口和右侧渐进抽屉，不跳入旧点联后台壳；返回后仍保留企业工作上下文。
4. 点联内部运营后台单独使用平台路由和平台会话，不在企业导航中混入模板发布、供应商费率或跨租户统计。
5. Web、App、小程序和桌面端复用同一认证、权限、领域状态和 API；各端只调整布局与交互密度。

## 6. 当前实现状态

- 已实现：统一账号登录、Bearer JWT/Refresh Token 契约、企业会话与平台会话分离、企业管理员从同一登录态进入员工管理、企业员工模板/实例分离、配置版本与启用状态机。
- 已冻结但尚未实现：`MemoryCandidate / MemoryItem / MemoryScope / Conflict` 的 Java 模块、数据库表、检索写入与治理页面。当前迁移只登记了 `USER_AGENT / GROUP_AGENT` 等权限作用域名称，不能据此宣称长期记忆已经可运行。
- 后续实现顺序：先完成企业工作平台的真实消息/群聊和单员工工作空间，再落 Memory Service 与作用域隔离；平台运营后台按模板、模型、价格和租户账务独立推进。
